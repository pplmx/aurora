# Roadmap: Aurora v1.75 Consistent Online Backups (ISS-082)

**Status:** Complete ✅
**Milestone:** v1.75 stop silent backup staleness under a live server; purge stale WAL on restore
**Started:** 2026-08-25

## Overview

`BackupService.Create` opened each source, ran `PRAGMA wal_checkpoint(TRUNCATE)`,
**ignoring the return value** (it is a result row — `busy`, `log`,
`checkpointed` — not an SQL error, so a partial/busy checkpoint "succeeded"),
then file-copied the bare `.db` (never the `-wal`/`-shm`). Under the running
server's seven pooled connections to the same file, the checkpoint almost
never fully drains the WAL, and any commit landing between the checkpoint and
the copy goes into a fresh `-wal` that is discarded: the archived `.db` was
**silently stale** — recent committed transactions missing — while
`metadata.json` was written and checksummed as a valid archive. Restore then
placed the restored file next to the still-present old `-wal`/`-shm`, which
SQLite would replay against the mismatched `.db` on next open.

`Create` now snapshots each source with **`VACUUM INTO`**, SQLite's
online-backup statement: it writes a complete, self-contained snapshot —
committed WAL frames included — to a fresh file even while the live server
keeps writing, so the archive reflects exactly the committed state at snapshot
time. Destinations that exist as directories are rejected explicitly, and the
v1.65 self-overwrite guard (`os.SameFile`) is preserved. `Restore` additionally
removes any leftover `-wal`/`-shm` beside the restored file so a pre-restore
WAL can never replay against the restored `.db`.
