# Roadmap: Aurora v1.71 Bounded API Request Bodies (ISS-077)

**Status:** Complete ✅
**Milestone:** v1.71 cap JSON request bodies so oversized payloads cannot exhaust server memory
**Started:** 2026-08-25

## Overview

No API handler bounded the request body — there was no `http.MaxBytesReader`
anywhere in the codebase — and per-client rate limiting is **off by default**
(`api.rateLimit.enabled=false`). A client holding the API key could therefore
POST an arbitrarily large JSON body (e.g. a fake lottery `participants` array,
which the domain allows up to 10k entries) and the `json.Decoder` would
materialize every element, letting a small number of connections force large
heap allocations and pressure the server toward OOM. This is the same
key-holder threat model the backlog has closed before (unbounded `?limit`
scans — ISS-003 — and slowloris server timeouts — ISS-065).

The fix enforces a body boundary in one place and maps overflow to a proper
client error:

- **`apimw.BodyLimit`** wraps `r.Body` in `http.MaxBytesReader` (4 MiB) and is
  registered **outermost** in the protected `/api/v1` group — before the
  optional rate limiter and before `APIKeyAuth` — so the cap applies whether
  or not the limiter is enabled and even to unauthenticated abuse that auth is
  about to reject.
- **`handler.decodeJSON`** replaces the 17 identical
  `json.NewDecoder(r.Body).Decode(&req)` blocks across token/oracle/nft/
  lottery/voting; it maps a body that trips the cap to **413 BODY_TOO_LARGE**
  (a distinct, actionable client error) instead of the generic 400
  `invalid request`.

The 4 MiB cap comfortably fits the largest legitimate payload (10k lottery
participants ≈ 1MB JSON) while bounding single-request memory.

- [x] No `json.NewDecoder(r.Body).Decode` remains outside the `decodeJSON`
      helper (17 call sites consolidated).

      (200); an over-cap stream trips `MaxBytesReader` and the handler

## Deep-Dive Origin

Second consecutive deep-dive round (backlog empty after v1.70): a targeted
scan for unbounded-input smells surfaced that the API group trusts arbitrary
body sizes while rate limiting is off by default — a coherent follow-on to the
earlier key-holder DoS hardening (ISS-003, ISS-065).
