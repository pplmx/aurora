# Roadmap: Aurora v1.55 Backup Content-Integrity Checksums

**Status:** Complete ✅
**Milestone:** v1.55 Backup content-integrity checksums
**Started:** 2026-08-23

## Overview

`BackupService.Verify` (and therefore `Restore`, which verifies first) checked
the integrity of a backup only by:
1. hashing the **metadata JSON** (Version/Timestamp/Databases/SchemaVersion), and
2. confirming each `.db` opens and contains at least one table.

It never hashed the actual database **file contents**. A truncated or
bit-corrupted `.db` that still opened with ≥1 table passed verification and
could be restored over a good database — silently restoring corrupt data.

## Success Criteria

- [x] Backup metadata records a per-database SHA-256 of each `.db` file content
      at `Create` time (`database_checksums`).
- [x] `Verify` (and so `Restore`) compares each backed-up DB's current content
      against its recorded checksum and rejects on mismatch.
- [x] Backward compatible: metadata produced by older versions (no
      `database_checksums` field, `omitempty`) still verifies via the existing
      table-presence check.
- [x] Regression test `TestBackupService_Verify_DetectsDBContentCorruption`
      proves a content-corrupted-but-still-readable DB is rejected.
- [x] `go build ./...` green; `go test -race ./...` green; `gofmt`/`go vet` clean.
