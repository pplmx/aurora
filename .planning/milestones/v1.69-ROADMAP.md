# Roadmap: Aurora v1.69 Rate-Limit Spoof Bypass (ISS-073)

**Status:** Complete ✅
**Milestone:** v1.69 key the rate-limit budget on the true socket peer
**Started:** 2026-08-24

## Overview

Per-client rate limiting was spoof-bypassable. `clientRateKey` derived its key
from `r.RemoteAddr` **after** chi's `RealIP` middleware had already overwritten
it from `X-Forwarded-For` / `X-Real-IP` / `True-Client-IP`
**unconditionally** — there was no trusted-proxy configuration, so the
limiter believed any client-supplied forwarded header. An attacker who rotated
those headers per request landed in a fresh bucket every time and never hit
429.

The fix captures the **socket-level peer** in a new `PeerIP` middleware that
runs **outer** to chi's `RealIP` (snapshotting `r.RemoteAddr` into the request
context before header substitution), and keys the budget on that peer. The
forwarded headers are believed **only** when the direct peer is on the new
`api.rateLimit.trustedProxies` allow-list (CIDRs or single IPs) — i.e. the
proxy/CDN that actually forwards to us. The default is an **empty** list:
every client keys on its socket peer, so spoofed forwarded headers can never
rotate past the budget. Malformed allow-list entries are dropped fail-safe
(an unparseable proxy is never trusted, which can only over-restrict, never
under-restrict).

## Success Criteria

- [x] `PeerIP` middleware captured before chi `RealIP`; `clientRateKey` keys on
      the socket peer and falls back to the (proxy-rewritten) remote address
      only when the peer is on the trusted-proxy allow-list.
- [x] New config `api.rateLimit.trustedProxies` (default empty; parses CIDRs
      and single IPs, self-test in `internal/config/config_test.go`).
- [x] Regression `TestRateLimit_RejectsSpoofedForwardedHeaderRotation`:
      one fixed socket peer rotating `X-Forwarded-For` four times still hits
      429 on the third request (pre-fix it never did).
- [x] `TestRateLimit_TrustsForwardedClientBehindConfiguredProxy` and
      `TestRateLimit_UntrustedPeerNeverTrustsHeaders` pin the trust model:
      distinct clients behind our configured proxy keep distinct budgets; an
      untrusted peer forging a proxy's forwarded client stays on its own peer.
