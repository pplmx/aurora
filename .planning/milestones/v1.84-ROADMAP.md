# Roadmap: Aurora v1.84 Voting Client-Error Classification Sweep

**Status:** Complete ✅
**Milestone:** v1.84 bug-fix (ISS-113..114)
**Started / Closed:** 2026-08-27

## Overview

Round-96 deep-dive (two parallel agents: voting/NFT service layers and
replay/nonce/outbox) surfaced two verified, unambiguous voting defects plus a
set of findings that were deliberately NOT turned into tasks because they are
documented design or previously-parked decisions:

1. **Voting CastVote: a valid-base64 but wrong-length private key returned
   HTTP 500** (ISS-113, TASK-121). `Ed25519Service.SignVote` rejects the
   length with a plain `fmt.Errorf("invalid private key size")` that
   `classifyError` does not match; only malformed base64 was already a 400
   (TASK-095). The NFT boundary enforces key lengths → `ErrInvalidPrivateKey`
   → 400; voting was inconsistent with it and with its own
   `ErrInvalidBase64`. Fixed: new `voting.ErrInvalidPrivateKey` sentinel,
   length check in `CastVoteUseCase` after decode, classified as
   400 `INVALID_PRIVATE_KEY`.
2. **Voting session roster accepted duplicate candidate IDs, doubling
   results** (ISS-114, TASK-122). `CreateSessionUseCase` validated existence
   but never de-duplicated, so `["c1","c1"]` (API) or `-c c1 -c c1` (CLI)
   made `GetResults` sum the candidate twice and render it twice. Fixed: new
   `voting.ErrDuplicateCandidate` sentinel, rejected before the existence
   scan, classified as 400 `DUPLICATE_CANDIDATE`.
3. **Triage decisions (recorded as DEC-005)**: the global `voters.has_voted`
   flag, draft/in-window sessions accepting votes, and `session start` being a
   non-enforcement lifecycle action are the DOCUMENTED, TESTED voting contract
   (v1.10 smoke test step 8, DEC-004) — not re-litigated. NFT transfer to an
   all-zero key (blackhole) is a product-semantics question (asymmetric with
   the token domain's `ErrTransferToZero`) — parked pending operator intent,
   not a silent code change. Burn's missing balance pre-check produces a
   phantom on-chain block on failed burns, but that is the EXACT class
   DEC-002 already parked (cross-DB atomicity; best-effort on-chain audit
   blocks never corrupt committed balances); evidence EV-044 records the
   congruence with no new task.
