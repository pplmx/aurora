# Roadmap: Aurora v1.73 API Server Secrets & Audit Wiring (ISS-079 + ISS-080)

**Status:** Complete ✅
**Milestone:** v1.73 fix the cmd/api boundary so the production HTTP server starts with the operator's key and actually persists its audit trail
**Started:** 2026-08-25

## Overview

A parallel fleet deep-dive over `cmd/api` + `internal/config` surfaced two
production-wiring defects at the same boundary (both verified end-to-end, one
by actually running the binary):

**ISS-079 — AURORA_API_KEY never reaches the API server.** `config.Load()` is
called **only** by `cmd/api/main.go`, and it never invoked
`viper.AutomaticEnv()`/`BindEnv` — the CLI's `AutomaticEnv` lives in
`root.go:119` and is not part of the API binary. Even viper's default env
matching would look for `API.KEY`, not `AURORA_API_KEY`. So `cfg.API.Key` was
always `""`: in production `resolveAPIKey("")` returned `ErrMissingAPIKey` and
the server refused to start **even with a correct `AURORA_API_KEY` set**; in
dev it minted and printed a fresh random key on **every** boot — a new secret
each restart that silently invalidated the key already embedded in previously
served web pages. The fix binds the documented variable inside `Load()` so
both modes honor the operator's key.

**ISS-080 — the HTTP server drops its entire audit trail.** `server.go` built a
bare `SyncEventBus` and passed it to `token.NewService`, but never subscribed
anything — the `AuditHandler`/`StatsHandler` subscriptions existed **only** in
the CLI wiring (`app/wire.go`). Every `mint`/`transfer`/`approve`/`burn`/
`transfer_from` audit event the service published over HTTP was silently
discarded, so `GetTransferHistory` read an empty event store and
`GET /api/v1/token/history` was **permanently empty on the production path** —
the very trail the ISS-074 (v1.68) post-commit-publish fix was written to
protect. The fix subscribes the same handlers server-side.
