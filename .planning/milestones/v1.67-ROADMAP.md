# Roadmap: Aurora v1.67 Atomic ClaimNextNonce

**Status:** Complete ✅
**Milestone:** v1.67 ClaimNextNonce atomicity under a real connection pool
**Started:** 2026-08-24

## Overview

`SQLiteReplayProtection.ClaimNextNonce` ran the nonce increment as
`Begin()` → `SELECT nonce` → `INSERT ... ON CONFLICT DO UPDATE` inside one
*deferred* transaction. A deferred tx takes its read snapshot **before** it
holds the write lock, so with a real connection pool (more than one open
connection to the same WAL file) two goroutines could both read `nonce=N`;
the loser of the write race then surfaced `SQLITE_BUSY` /
`SQLITE_BUSY_SNAPSHOT` (or, without WAL, silently wrote a duplicate nonce and
let two transfers sign with the same value). The existing concurrent test
never caught it because it forced `SetMaxOpenConns(1)`, serializing every
claim onto one connection.

The method is now a single atomic
`INSERT ... ON CONFLICT(token_id, owner) DO UPDATE SET nonce = nonces.nonce + 1
RETURNING nonce`: SQLite executes a standalone statement atomically and reads
back its own result, so every caller increments the current high-water mark
exactly once regardless of interleaving. The replay DSN also gains
`_busy_timeout=5000` so a claimant that finds the write lock momentarily held
waits instead of erroring.
