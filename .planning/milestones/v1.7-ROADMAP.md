# Roadmap: Aurora v1.7 Web UI Parity

**Status:** In progress
**Milestone:** v1.7 Web UI Parity
**Started:** 2026-08-22

## Overview

Make the documented browser Web UI actually functional against the real
voting API. An audit of `web/` found the voting page is a facade:
`web/js/app.js` `createVote()` POSTs to `/api/v1/voting/create` — which is not
a registered route (404) — and `castVote()` is an `alert()` stub. The page's
model (title / owner / yes-no) does not match the real voting domain
(candidates, sessions with candidate rosters, Ed25519-signed ballots). The
audit also surfaced an API gap: sessions could be created but never listed.

## Success Criteria

- [x] `GET /api/v1/voting/sessions` lists sessions (repo `ListSessions()` was
      already implemented; added use case + handler + tests) (00ab212)
- [ ] `web/voting.html` / `web/js/app.js` use only real API endpoints and
      perform real actions (create session, list sessions, cast a signed vote)
- [ ] The lottery page + dashboard work against real endpoints (audited: they
      already do — lottery `create`/`history` and voting `candidates` resolve)
