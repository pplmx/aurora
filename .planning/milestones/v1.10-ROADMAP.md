# Roadmap: Aurora v1.10 Authenticity & Defensive Hardening

**Status:** In progress
**Milestone:** v1.10 Authenticity & Defensive Hardening
**Started:** 2026-08-23

## Overview

v1.9 (API Hardening & Deep Dive) closed pagination caps, the ended-session
lifecycle, and the token approve/allowance CLI↔API gap. v1.10 tackles the most
serious class of issue a design audit can surface: code paths where a claimed
identity (signature / key) is stored or trusted without being verified against
the authoritative identity it claims. The first confirmed case is a ballot
forgery on the voting path.

## Success Criteria

- [ ] Enforce ballot authenticity: `CastVote` must verify the presented
      private key corresponds to the registered voter's public key (the
      signature is produced with the caller's key and checked against the
      voter's stored public key). (found: `VerifyVote` was defined but never
      called → forged ballots were accepted).
- [ ] Enforce NFT key↔owner binding on `Transfer`/`Burn`: the presented
      private key must correspond to the `from`/`owner` public key (was
      missing — knowing only a public key let a caller transfer/burn an NFT
      with their own key; token module already had `VerifyPrivateKeyMatches`).
- [ ] Full `go test -race ./...` green.
