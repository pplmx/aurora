# Roadmap: Aurora v1.74 Bounded Metrics Label Cardinality (ISS-081)

**Status:** Complete ✅
**Milestone:** v1.74 stop attacker-chosen path segments from growing the metrics registry / /metrics payload without bound
**Started:** 2026-08-25

## Overview

`classifyModule` labelled each request by the **raw third URL path segment**
(`/api/v1/<segment>/…`), and the metrics middleware is registered **first**
(outermost) in the router — before `APIKeyAuth` and before route matching, so
even 404s to unknown paths are observed. An unauthenticated client could
therefore request `/api/v1/arbitrary-0/…`, `/api/v1/arbitrary-1/…`, … and every
distinct segment added a permanent entry to two nested maps under the mutex
(`moduleTotal[module]` + a per-module status sub-map, **never evicted**), while
the (also unauthenticated) `/metrics` handler rendered every label — unbounded
memory growth and Prometheus cardinality blow-up on the default config (rate
limiting disabled). The original doc-comment's claim that grouping "keeps the
label cardinality bounded" only held while every segment was one of the five
real modules.

`classifyModule` now emits a label **only** for the fixed set of registered
route roots (`token`, `nft`, `voting`, `lottery`, `oracle`, `blockchain`) and
folds every other path under `/api/v1/` into a single `other` bucket. HTTP
status codes remain bounded by the finite status space; latency buckets are a
fixed histogram — so the registry's sizes are now constant regardless of input.
