# Roadmap: Aurora v1.70 SQLite Writer Contention (ISS-076)

**Status:** Complete ✅
**Milestone:** v1.70 serialize SQLite writers so concurrent transfers no longer fail with SQLITE_BUSY
**Started:** 2026-08-25

## Overview

Multi-statement write transactions (`Mint`/`Transfer`/`TransferFrom`/`Burn`,
voting vote-creation, NFT writes) began with a **deferred** `BEGIN`, took a
read snapshot, and acquired the SQLite write lock **mid-transaction**. Over
the API's real, unlimited connection pool (`SetMaxOpenConns` is never capped
in production wiring), two concurrent writers collide: one wins the lock, the
other fails with `SQLITE_BUSY` ("database is locked"). And because no
production DSN set `_busy_timeout` (only the v1.67 replay DSN did), there was
no wait-and-retry — the losing transaction errored immediately and surfaced
as a spurious HTTP 500 through the error-classification layer.

Verified before the fix: 16 concurrent transfer-shaped read-then-write
transactions over an unlimited pool failed **10/16** with "database is
locked" (6/16, 7/16, 10/16 across runs). A directly-connected attacker does
not even need to try to trigger it — it is ordinary concurrent usage.

The fix hardens every write-path DSN:

- **`_txlock=immediate`** — every `db.Begin()` executes `BEGIN IMMEDIATE`,
  acquiring the write lock at `BEGIN`. Writers serialize up front, which
  removes the deferred read-then-write window that produces the fatal,
  un-maskable `SQLITE_BUSY_SNAPSHOT` (`_busy_timeout` alone cannot wait on
  that one).
- **`_busy_timeout=5000`** — a contender whose `BEGIN IMMEDIATE` finds the
  lock held waits up to 5s instead of failing (same value as the v1.67 replay
  DSN).

Repository DSNs share a new `dsn()` helper + `writeDSNSuffix` const
(`internal/infra/sqlite/dsn.go`): token, nft, lottery, oracle. The
blockchain/voting singleton DB (`InitDB`) carries the same suffix inline. The
event store — which only ever autocommits single `INSERT`s — adds
`_busy_timeout` (no `_txlock` needed). Backup/migrate are administrative or
startup-serialized read paths and are deliberately left unchanged.

## Deep-Dive Origin

Backlog was empty after v1.69, so this candidate came from a fresh
deep-dive scan of the infra/sqlite layer — the same class of failure
(real-pool contention) that IIS-075 surfaced in the replay path but left
latent in every other write DSN.
